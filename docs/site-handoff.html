Site handoff guide

Everything you need to run the Everything Energy site after handoff: how pages and blocks are authored in Experience Workspace (DA), how templates and the brand styles work, how to make single edits and site-wide changes, how to use the AI assistant, and how to preview and publish.

The site has English (/en/), Spanish (/es/) and a set of top-level pages without a language prefix. Content lives in Experience Workspace at adobedrago/nrg; code lives in the AdobeDrago/nrg repository.

Who owns what

Authors and marketers own page copy, images, links, page and section metadata, the nav and footer documents, the plans and ZIP data sheets, and preview/publish. Developers own block code and styles, the code templates, design tokens, the search and query indexes (helix-query.yaml), the provider brand list used by Plan Cards, and anything the assistant cannot do safely on its own.

How individual blocks are authored

A page is a document. Plain headings, paragraphs, lists and images are default content. Designed components are blocks. In the document a block is a table: the first, shaded row holds the block's name, and the rows below hold its content. The site reads the name to decide how to display the content, and each block reads its rows and cells in a particular order, which the block catalog documents for every block.

Example: a Provider Contact block as it appears in the document
Provider Contact
H3: Contact Reliant
Shoppers in Texas can contact us via online chat, phone or email.
Call us at (833) 577-2884.

Rules that apply to every block

  • Keep the name row exact. The name is matched case-insensitively with spaces turned into hyphens: Provider Hero loads provider-hero. A typo leaves the block unstyled.
  • Variants go in brackets after the name: Provider Hero (areas). Only variants listed in the catalog do anything.
  • Rows and cells are read by position for most blocks. Keep the order, and leave an optional row empty rather than deleting it when the catalog says so.
  • Images: drag images straight into the cell; DA uploads them next to the page. Set alt text on meaningful images (right-click the image). Decorative backgrounds ignore alt text.
  • Sections are separated by a horizontal rule (---). Each section becomes a band on the page and can be configured with a Section Metadata table (see Branding).
  • Page metadata goes in a Metadata table at the end of the page: Title, Description, Image, and when needed Template and Theme.

Inserting blocks

In Experience Workspace, open a page and choose Content mode, then press / and choose a block, or open the tools panel and use Outline (hover a section, then add block) or Blocks. The blocks offered come from the site's block library (/tools/sidekick/library/blocks.json in DA). The most reliable way to get a correct structure is still to copy the block from an existing page listed in the catalog.

Block library needs a clean-up. The library currently registers Accordion (no such block exists in the code), contains three empty rows, and has example pages for Tabs and for Hero and Cards variants that the code does not style. Until a developer fixes it, copy blocks from the pages linked in the catalog. See Open items.

Implementing the brand: headings, links, buttons, lists and sections

Authors don't pick colors or fonts. The brand is applied by the style system from the structure you author, so using the right element is how you apply the brand.

Headings

All headings use Source Sans 3 in bold, in the brand navy (light theme). Sizes step down from H1 to H6, and H1–H3 switch to a larger desktop scale at 900px. Use one H1 per page, then H2 for sections and H3/H4 inside blocks as the catalog shows. Some blocks add their own treatment to a heading, such as the pink accent bar under the FAQ Hero title.

Links and buttons

Formatting decides how a link looks. A link becomes a button only when it is the only thing in its paragraph.

Lists

Bulleted and numbered lists use the body text color and size. Several blocks give lists their own design: Area List turns a list of links into a city grid, Provider List shows feature bullets, the footer turns each heading-plus-list into a column, and the nav's list becomes the menu. Keep list items short, and use links inside list items where the catalog calls for them.

Quick edit routine

  1. Open the page in Experience Workspace (or use Edit in the Sidekick from the preview page).
  2. Make the change in Layout mode. Check the result in Split view if the block has several rows.
  3. Use the Send menu → Preview, check the page at desktop and phone width, then Publish.
  4. If something goes wrong, open Version History to compare or restore the previous version.

Content that repeats but is authored on each page

Two blocks hold the same kind of content on many pages but are typed into each page separately: Fetch Plans (149 pages) and Popular Areas (125 pages). Changing their wording everywhere is a bulk edit:

  • Short term: ask the assistant to make the same change across the folder (see full-fledged chat authoring), then preview and publish the changed pages with the Bulk app.
  • Recommended: have a developer move the shared Fetch Plans copy into a Fragment (for example /en/fragments/fetch-plans) or into the template code, so the next change is a single edit.

Page metadata that should be the same across a folder (for example a default social image for all area pages) can also be managed centrally with a bulk metadata sheet. This site doesn't use one yet; a developer can add it.

Design system approach and dark mode

The site's styling is a layered token system, documented in full in the style system guide. In short:

  1. Palette tokens name raw colors (--palette-purple-500 is #7564c1).
  2. Semantic roles describe a purpose (--color-text-primary, --color-surface-raised, --color-link). Blocks use roles, never hex values.
  3. Themes remap roles: the light theme is the foundation in styles/brand.css; the dark theme in styles/themes.css overrides roles only, so every block follows without changes.
  4. Sections can switch scheme and layout through Section Metadata.
  5. Blocks own their internal layout and any brand artwork (gradients, photos), which stays the same in both themes.

Extending the system

  • Change a color everywhere: edit its semantic role in brand.css (and its dark value in themes.css).
  • Add a block: use semantic roles only; choose its surface (raised for cards) and bind its foreground hooks so it stays readable in dark sections.
  • Third-party logos: put them on the logo plate tokens so they get a light plate in dark mode.
  • Check every change in both themes and inside a Color Scheme: dark section, at phone and desktop widths.

Demo: dark mode

Dark mode is chosen in this order: a page's Theme metadata (pins the page), then the visitor's switch, then the device setting, then light.

  1. Open any page, for example the English homepage.
  2. Select Menu and turn on Dark mode (Modo oscuro on Spanish pages). The page switches instantly and the choice is remembered on that device.
  3. Browse to a provider page, a ZIP search such as 75001, and the FAQs to show how cards, plan results and forms adapt while brand artwork stays the same.
  4. To show the automatic behavior, turn the switch off, clear the site's data in the browser, and change the operating system's appearance to dark: the site follows it live.
  5. To show pinning, add Theme | light to a page's Metadata: the switch disappears on that page.

Known dark-mode gap: the benefit icons on provider pages are authored PNGs in dark purple line art, so they have low contrast on dark cards (visible in the provider screenshot above). Options: upload light versions, or have a developer add a light plate behind Details Cards icons in dark mode.

Chat-based authoring: content only

Experience Workspace includes an Assistant panel (the AI chat available in most windows). In content-only mode you use it to change what the page says without changing its structure: no blocks added, removed or renamed, and no change to rows, cells, templates or metadata keys.

Good content-only tasks

  • Rewrite or shorten copy in a block, keeping its rows and cells.
  • Fix spelling, tone and terminology across a page.
  • Write or improve alt text, page titles and descriptions.
  • Draft Spanish copy for a page from its English version for a translator to review.
  • Fix preflight warnings such as a missing H1 or title.

Example prompts

On this page, rewrite the intro paragraph in the Provider Hero to be under 50 words and more benefit-led. Don't change any other block.

Check every image on this page for missing or unhelpful alt text and suggest improvements. Apply them after I confirm.

Write a meta description under 155 characters for this page and put it in the Metadata table's Description row.

Translate the Details Cards copy on /en/providers/cirro into Spanish for /es/providers/cirro. Keep brand names and the table structure exactly the same.

Guardrails

  • Start prompts with the scope ("on this page", "in the Details Cards block only") and say what must not change.
  • The assistant asks for confirmation before it changes content; read the proposal before approving. Responses can be wrong.
  • Always preview the page before publishing an assistant change. Use Version History to undo.
  • Keep brand names, prices and legal text (PUCT registration, plan terms) exactly as supplied. Never let the assistant invent plan details.

Chat-based authoring: full-fledged

Full-fledged chat authoring lets the assistant change structure as well as content: create pages, insert templates and blocks, restructure sections and work across many pages. It is powerful and needs a review step every time.

What it can do on this site

  • Create pages from a template: "Create /en/areas-of-service/pflugerville from the Service Area Page template, using this copy…"
  • Add or rearrange blocks: "Add a Reviews Carousel after the Provider Cards on /en/ with these three reviews."
  • Apply section styling: "Put the Choice Guide on /en/providers/ in a section with Background subtle and Spacing l."
  • Fix pages to match the catalog: "Check every block on this page against the documented structure and fix rows that are out of order."
  • Multi-page edits: "In every page under /en/areas-of-service/, change the Fetch Plans button text to 'Compare plans'. List the pages you changed."
  • Maintain the block library: the assistant has already been used to fix the library pages (separating each example heading and block into their own sections).

Assistant memory and skills

The assistant keeps project memory in /.da/agent/memory.md and a log of recent changes in /.da/agent/recent-pages.json. Prompts and skills are managed from the + menu (Manage Prompts, Manage Coworker).

Correct the memory before relying on it. The current memory file describes blocks and variants that do not exist in the code (Accordion, Tabs, Hero "left aligned/centered/dark", Cards "icon/two-up") and treats the block library as the source of truth. Replace those entries with the block catalog in this guide, and add rules such as "use absolute content.da.live image URLs in library pages" that are still valid.

Developer-side AI agents

Developers also use coding agents (for example Claude Code with Adobe's AEM Edge Delivery skills) on the repository. These can build or change blocks, import pages from the original site, and push content to DA through its API. Treat them like any developer: work on a branch, open a pull request, review on a preview branch URL, and only then merge and publish.

Review checklist for structural changes

  1. Ask the assistant to list every page it changed.
  2. Open each page in Split view and check block names, row order and metadata.
  3. Preview all changed pages (one at a time, or with the Bulk app) and check desktop and phone widths.
  4. Publish only after review. Restore from Version History if needed.

Other bulk authoring operations

Bulk preview, publish, version, index and delete

The Bulk app (under Apps in Experience Workspace) runs one operation on a list of page addresses.

  1. Collect the addresses: in the content browser, tick documents (or the folder's select-all box) and choose Share to copy their URLs. The Traverse tool lists everything below a folder.
  2. Open Apps → Bulk, paste the URLs, choose an operation (Preview, Publish, Version, Index or Delete) and select Submit.
  3. Watch the Remaining, Errors, Success and Total counts; open each category to see which pages failed.

Delete removes pages from the preview and live sites and from the indexes. It does not delete the documents themselves. Use it to take pages down; delete the documents separately if they are no longer needed.

Data sheets

The plans and ZIP data is edited as a spreadsheet, which is itself a bulk operation: one sheet edit updates every ZIP search. See the plans sheet column guide.

Translation projects

Translation is configured for this site (English as the source language, Google as the service, merge on rollout to keep regional edits). Use Translation Projects to send a set of English pages for translation and roll the results out to /es/, then review and publish the Spanish pages.

Search and query indexes

Two indexes are built automatically when pages are published: /query-index.json (used by the Blog List) and /search-index.json (used by the FAQ search). If a published page is missing from search, run Index on it with the Bulk app. Index fields are defined by developers in helix-query.yaml.

Snapshots

A snapshot groups several pages, across languages if needed, so they can be reviewed and published together, for example a new provider in English and Spanish. Each page gets a shareable review URL (optionally password-protected). Request review locks the snapshot; a reviewer then chooses Approve & publish to release the whole group or Reject & unlock to send it back. Scheduled publishing is an early-access option Adobe must enable.

Preview and publication workflows

Saving happens automatically in Experience Workspace, but the website only changes when you preview or publish. Code changes are separate: they go live when merged to main.

Single page

  1. In the editor, open the Send menu and choose Preview. The preview page opens in a new tab on main--nrg--adobedrago.aem.page.
  2. Check the page at desktop and phone width, in light and dark mode, and test its links and forms (a ZIP search for plan pages).
  3. Optionally run the preflight checks from the Prepare menu (for example a missing H1 or page title).
  4. Open the Send menu again and choose Publish. The live page opens on main--nrg--adobedrago.aem.live.
  5. From a preview or live page you can also use the Sidekick browser extension to publish, unpublish or jump back to editing.

Sheets, nav, footer and media

  • Sheets (plans, ZIPs, redirects) are previewed and published like pages. Preview first and test a ZIP search before publishing.
  • Nav and footer are documents: publish them and every page in that language picks up the change without republishing the pages.
  • Images are published with the page that uses them.

Many pages

Use the Bulk app to preview or publish a list of pages, or a snapshot for a coordinated release. Publish in dependency order: target pages first, then sheets, then the pages and navigation that link to them.

Taking a page down

  1. Open the Prepare menu and choose Unpublish, type YES and confirm. This removes both the preview and live versions.
  2. Remove links to the page from navigation, footer and listings, and add a redirect in redirects.json if the address had traffic.

Release checklist

  1. One H1; Metadata Title, Description and Image filled in; Template set where required.
  2. Block names and row order match the catalog; no example text left from a template.
  3. Checked on preview at desktop and phone width, light and dark.
  4. Any code the content depends on (for example a new provider brand) is already merged to main.
  5. Published, then checked on the live site in a private window.

Maintenance and technical reference

Code is deployed from main by Code Sync; content is published from Experience Workspace. Run the site locally with aem up --url https://main--nrg--adobedrago.aem.page from the repository and open http://localhost:3000/en/. Run npm run lint before opening a pull request.

Experience Workspace is turned on with the ew.enabled flag in the site or organization config, and the Sidekick's edit link can point to the canvas editor (https://da.live/canvas#/{{org}}/{{site}}{{pathname}}).
